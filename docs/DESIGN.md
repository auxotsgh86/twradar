## 1. 現況問題（v0.1.3 報表 2026/11/12 檢查結果）

1. 訊號矩陣缺「月線／趨勢」欄，相同 ✓✕ 組合卻得到不同燈號，看不出原因。
2. 「主力」欄永遠是「?」（沒有資料源）。
3. 法人判定為「外資或投信任一方買」即通過，未處理對作（例：元大金外資 +18,429 張、投信 −5,496 張仍亮加碼）。
4. 外資／投信圖以「張」比較，股價差距大時失真（元大金外資 18,429 張 ≈ 13 億元；創意投信 400 張 ≈ 31 億元）。改用金額或佔成交量比例。
5. 燈號（綠＝好、紅＝壞）與漲跌（紅漲綠跌）顏色語意衝突。

## 2. 架構總覽

```
資料源 Provider（可注入） → 標準資料（SQLite）
        → 指標 Indicators（MA、均量、連買天數…）
        → 條件 Conditions（內建＋使用者自訂比較式）
        → 規則 Playbooks（加碼面／持有面，由上往下第一條符合）
        → 狀態確認（連續 N 日才轉換燈號）
        → 訊號＋判定軌跡（trace）→ API／網頁／報表
設定 settings.json ──────────────┘（每一層都讀它）
```

## 3. 資料源（DI）

### 3.1 介面（P1 已實作，`twradar/providers/`）

```python
class Provider:
    id: str                       # "twse", "tpex", "finmind" ...
    scope: str                    # "market"：某天全市場；"stock"：逐檔一段期間
    markets: tuple[str, ...]      # 涵蓋的市場，例如 ("TWSE",)
    datasets: tuple[str, ...]     # 依抓取順序，例如 ("quotes", "inst", "margin", "flows")
    def fetch(self, dataset, d) -> Batch: ...                                # scope="market"
    def fetch_stock(self, code, market, start, end, datasets) -> Batch: ...  # scope="stock"
    def confirm_no_trading(self, d) -> bool: ...                             # 休市確認
    def doctor(self, d) -> list[(label, fn)]: ...                            # twradar doctor
```

- **Batch**：`{"quotes": [...], "inst": [...], "margin": [...], "market": [...]}`，每列已是資料庫格式；單位在 Provider 內統一（成交量、法人 = 股；融資券 = 張；金額 = 元）。
- **Transport（HTTP）注入**：Provider 不自己開連線；`Crawler(db, cfg, transport=..., primary=[...], fallback=[...])` 都可注入，測試用假伺服器或記憶體資料源。
- **Registry**：`@register` 註冊；新增來源 = 在 `providers/` 新增一個檔案並在 `__init__.py` import。
- **抓取步驟** = 每個 primary 資料源 × 它的 datasets，步驟 id 為 `{provider}_{dataset}`（與 v0.1.3 相同，API 不變）。

### 3.2 設定

```json
"sources": {
  "primary":  ["twse", "tpex"],
  "fallback": ["finmind"],
  "options":  { "finmind": { "token": "" } }
}
```

- primary 依序抓全市場資料；某市場某資料集失敗時，fallback 依序逐檔補觀察清單（只抓缺的資料集，不覆蓋已成功的官方資料）。
- `options.<id>.base` 可改網址（測試用）。
- 存在 `settings.json` 的 `sources`；v0.1 的 `config.json` 欄位（`use_finmind_fallback`、`finmind_token`）升級時自動搬過來。
- 設定的資料源變更後，下一次抓取前自動重建（`Crawler.refresh()`），不必重啟。

### 3.3 條件與資料的關係

每個條件宣告需要的欄位（例如 `marginChg`）。缺資料時自動標為 `na`（資料不足），不必在判定程式中手寫缺漏處理。

## 4. 條件與規則框架

### 4.1 條件（Condition）

兩種：

1. **內建條件**（Python，需要歷史序列或較複雜計算）：
   `inst.foreignStreak`、`inst.trustStreak`、`inst.amplify`、`inst.conflict`（法人對作）、`pv.blowoffBlack`（爆量長黑）…
   每個內建條件宣告參數表（名稱、型別、預設值、說明），網頁依此產生輸入欄。
2. **比較條件**（網頁新增，不必寫程式）：
   `左邊 運算子 右邊`，左右可以是欄位、數字、參數，或「欄位 × (1 ± 參數%)」。
   ```json
   { "id": "aboveMa20", "label": "站上月線",
     "left": "close", "op": ">=", "right": { "field": "ma20", "pct": "-maTol" } }
   ```
   只允許白名單欄位與運算子，**不使用 eval**。

條件結果：

```json
{ "id": "aboveMa20", "state": "pass|fail|na", "value": 2340, "target": 2343.47,
  "text": "收盤 2,340 / 月線 2,355.25", "need": "站上月線 2,343.47（差 3.47）" }
```

### 4.2 參數（Params）

- 全域參數表，網頁可新增、修改、刪除（被引用中的參數不可刪）。
- 每個參數：`id`、`label`、`value`、`unit`、`min`/`max`、`note`。
- 條件以 `"param:maTol"` 引用。

### 4.3 規則（Playbook）

- 兩組：`entry`（加碼面）、`hold`（持有面）。
- 每組是**由上往下**的判定規則，第一條符合者決定燈號；最後一條為預設。
- 組合語法：`all`、`any`、`atLeast: {n, of: [...]}`、`none`。

```json
"playbooks": {
  "entry": [
    { "light": "noAdd", "when": { "any": ["belowMa20Tol", "chipDivergence", "blowoffBlack", "inst.conflict"] } },
    { "light": "add",   "when": { "all": ["pvConfirm", { "atLeast": { "n": 2, "of": ["instBuying", "mainBuying", "retailClean"] } }] } },
    { "light": "watch", "default": true }
  ],
  "hold": [
    { "light": "exit",   "label": "停損",     "when": { "any": ["stopLoss", "belowKeyLevel", { "all": ["belowMa20", "instSellStreak"] }] } },
    { "light": "exit",   "label": "獲利出場", "when": { "all": ["profitTarget", { "any": ["belowMa20", { "atLeast": { "n": 3, "of": ["whaleDown", "retailUp", "marginHigh", "instSellStreak"] } }] }] } },
    { "light": "reduce", "label": "獲利保護", "when": { "all": ["profitTarget", { "atLeast": { "n": 2, "of": ["whaleDown", "retailUp", "marginHigh", "instSellStreak"] } }] } },
    { "light": "reduce", "label": "過熱",     "when": { "any": ["failedLimitUp", "limitUpOpenBlowoff", "ma20BiasHigh"] } },
    { "light": "keep",   "default": true }
  ]
}
```

> 以上為**初始範例**，條件與門檻由使用者自行調整。

### 4.4 「還差什麼」自動產生

- **加碼面**：找出最接近成立的 `add` 規則，列出其中 `fail` 條件的 `need`。
- **持有面**：列出已成立的減碼／出場條件（依據）與接近成立者（警示）。

### 4.5 狀態確認（避免燈號來回跳）

- 參數 `confirmDays`（預設 1 ＝ 不確認；可設 2）：新燈號需連續 N 日成立才轉換，期間顯示「轉換中」。
- 每日訊號存 `light`（確認後）與 `rawLight`（當日原始）。

### 4.6 軌跡與重現

每次分析把「當時的設定版本 hash」與所有條件結果一併存入 `signals`，日後可重現、回測。

## 5. 持有面（減碼／出場）

### 5.1 燈號

| 面向 | 燈號 |
|---|---|
| 加碼面 `entry` | 加碼 `add`／觀察 `watch`／不宜加碼 `noAdd` |
| 持有面 `hold` | 續抱 `keep`／減碼 `reduce`／出場 `exit` |

### 5.2 觀察清單欄位

新增 `holding`（是否持有，布林）。持有中的個股在報表上以持有面為主、加碼面為輔；未持有的個股只看加碼面。

### 5.3 持有成本（D7）

- 成本選填（`cost`、`shares`）。有填時提供欄位 `profitPct`（含手續費與證交稅估算），可在規則中引用。
- 只有規則中**明確引用** `profitPct` 的條件會受成本影響；其他條件只看市場資料。
- 報表顯示未實現損益；未填成本時，引用 `profitPct` 的條件為 `na`。

### 5.4 使用者目前的出場習慣（2026-11-13 討論）

使用者描述：
1. 獲利 ≥ 20%，且「大戶賣、散戶買、融資偏高」時出場。
2. 接近漲停但沒有量時，會考慮出場。

討論結果（D8 已採用）：
- 規則 1 只在獲利 ≥ 20% 時啟動，**虧損或小賺的部位沒有出場條件**，需補「停損／趨勢破壞」層。
- 「接近漲停」需分辨三種情況：
  - 鎖漲停且量縮：賣壓小，通常偏強，不列為出場。
  - 衝高接近漲停但沒鎖住、留長上影線、量縮：追價力道減弱 → 減碼候選。
  - 爆量打開漲停：籌碼換手 → 減碼／出場候選。
- 提議的持有面三層：

| 層 | 觸發 | 動作 |
|---|---|---|
| 停損（保護本金） | 跌破關鍵價；跌破月線＋法人連賣；或 `profitPct ≤ −10`（參數 `stopLossPct`） | 出場 |
| 獲利保護 | `profitPct ≥ 20`（參數 `profitTargetPct`）且籌碼轉弱任兩項（大戶減、散戶增、融資使用率高、法人連賣） | 減碼；三項以上或跌破月線 → 出場 |
| 過熱警示 | 衝高未鎖漲停留長上影、爆量開板、月線乖離過大 | 減碼 |

### 5.5 籌碼轉弱的資料對應

| 說法 | 指標 | 資料源 | 頻率 |
|---|---|---|---|
| 大戶賣 | 集保 ≥ 400 張（或 1000 張）持股比例週減 | 集保股權分散表 | 週 |
| 大戶賣（日資料近似） | 外資＋投信連賣 | 三大法人 | 日 |
| 散戶買 | 集保小額持股人數週增；融資增加 | 集保、融資券 | 週／日 |
| 融資偏高 | 融資使用率（餘額／限額），或融資餘額相對 60 日區間位置 | 融資券 | 日 |
| 沒鎖漲停 | 最高價接近漲停價，但收盤 < 最高價、上影線長 | 收盤行情 | 日 |

### 5.6 大戶門檻（D9）

- **預設千張大戶**（參數 `whaleMode = "lots"`、`whaleLots = 1000`），與市場慣例一致。
- **個股覆寫**：觀察清單欄位 `whaleLots`，例如高價股設 400 或 800 張。
- **市值模式**（`whaleMode = "amount"`、`whaleAmount = 100000000`）：換算張數 = `whaleAmount ÷ (股價 × 1000)`，再對到集保持股分級最接近的分級下限（1、5、10、15、20、30、40、50、100、200、400、600、800、1000 張）。
- **變化量用「佔總股數 %」衡量。** 集保表本身提供每級佔集保總股數的比例，股本大小因此自動被正規化。
- **不用本益比。** 本益比是評價指標，跟「多少錢算大戶」無關。
- 盤中大單、券商「實戶」是不同概念（需要逐筆成交資料／券商客戶資料），不採用。
- **市值模式的門檻要固定一段時間。** 股價變動會讓換算出的分級跳動，造成假的「大戶增減」。門檻依 60 日均價計算、每月重算一次；比較兩週時一律用同一組分級。
- **市值模式的上限問題。** 集保最高級為「1000 張以上」，低價股（例：元大金）換算超過 1000 張時只能用 1000 張，報表標註「門檻受限」。
- **雜訊提醒。** 1000 張以上分級包含 ETF、外資保管帳戶，權值股的大戶比例變化可能來自 ETF 申購買回，而非主力動作。

### 6.3 存檔規則

- 存檔前驗證（欄位、型別、引用的條件／參數是否存在、規則是否有 `default`），失敗不寫入並指出錯誤位置。
- 原子寫入（先寫暫存檔再改名），每次存檔保留前 20 版於 `settings.history/`，可在網頁還原。
- 網頁提供匯出／匯入 JSON、「恢復預設」。
- API token 等敏感值在網頁上遮蔽顯示。
- 從 v0.1.3 升級時，自動把 SQLite 的觀察清單（`stocks` 表）與門檻（`settings.rules`）、`config.json` 的排程與資料源轉成 `settings.json`，並從 `config.json` 移除這些舊欄位。
- 新版本新增的內建參數、欄位在載入時自動補上預設值（`normalize`）；內建參數被刪掉也會自動補回。
- 檔案被手動修改：自動重新載入；內容不合法就沿用上一個合法版本，並在「系統狀態」顯示錯誤（`settingsError`）。
- 觀察清單從 SQLite 移到 `settings.json`（SQLite `stocks` 表只保留供遷移）。

### 6.4 權限（D10）

| 角色 | 可以做 |
|---|---|
| 唯讀 `reader` | 讀取訊號、個股歷史、狀態（晨報使用） |
| 管理者 `admin` | 全部：改設定、觀察清單、手動抓取、匯出資料庫、查看與重設 token |

- **憑證**：
  - `readToken`：給晨報等自動化程式，放在網址或標頭。
  - `adminToken`：給管理用的腳本。
  - **管理密碼**：給網頁登入，可自己設成好記的密碼（以 PBKDF2 雜湊儲存）；登入後瀏覽器保持 30 天（HttpOnly、SameSite=Strict cookie）。
- **忘記怎麼辦**：
  - 忘記 token → 用管理密碼登入網頁，在「設定 → 權限」查看或重設。
  - 忘記管理密碼 → 在主機上執行 `twradar admin reset-password`，或看安裝時桌面產生的「連線資訊」檔。
- **升級**：v0.1.3 原本的 `token` 轉為 `readToken`（晨報不用改），另外產生 `adminToken` 與初始管理密碼，寫入 `twradar info` 與桌面連線資訊檔。
- **可替換**：驗證透過 `Authenticator` 介面（輸入 request，輸出 `Principal(role)`），日後可接外部權限系統而不改 API。
- 登入失敗計次：同一 IP 15 分鐘內失敗 5 次、或所有來源合計 20 次，鎖定 15 分鐘。
- 同時帶多種憑證（例如網址有唯讀 token、又已登入）時取權限最高者。
- `config.json`、`settings.json` 權限設為 600；服務啟動的紀錄不印出管理密碼與管理 token。
- CLI：`twradar admin reset-password`、`admin set-password`、`admin rotate-token read|admin`。
